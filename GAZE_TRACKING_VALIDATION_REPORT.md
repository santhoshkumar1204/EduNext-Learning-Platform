# Gaze Tracking Validation And Calibration Audit

Date: 2026-06-16

## Scope

This audit validates the current gaze tracking module only. It does not implement fusion, redesign the UI, or remove existing functionality.

## Implementation Map

- Raw gaze ratios are estimated in `src/analytics/gazeTracking.js`.
- Direction classification is handled in `src/analytics/gazeDirection.js`.
- Temporary guided calibration and accuracy reporting are handled in `src/analytics/gazeCalibration.js`.
- Rolling gaze metrics are handled in `src/analytics/gazeMetrics.js`.
- Runtime state is wired through `src/hooks/useGazeTracking.js`.
- The existing temporary debug panel displays the validation output in `src/components/GazeDebugPanel.jsx`.

## Raw Gaze Values

The debug panel now exposes the required raw values:

- Left eye horizontal ratio
- Right eye horizontal ratio
- Averaged horizontal ratio
- Left eye vertical ratio
- Right eye vertical ratio
- Averaged vertical ratio

The ratios are normalized inside each eye bounding box. A value around `0.500` means the iris center is near the geometric center of the eye box. Values are clamped to `0.000` through `1.000`.

## Threshold Verification

Current default thresholds:

- Center: horizontal `0.420` to `0.580`, vertical `0.380` to `0.620`
- Left: averaged horizontal ratio `< 0.420`
- Right: averaged horizontal ratio `> 0.580`
- Up: averaged vertical ratio `< 0.380`
- Down: averaged vertical ratio `> 0.620`

Center is not a standalone classifier threshold in the original implementation. It is the fallback direction when Left, Right, Up, and Down conditions do not match. The audit output now prints Center explicitly as the accepted horizontal and vertical ranges derived from those thresholds.

## Direction Logic

Classification uses the averaged horizontal and vertical ratios. It first compares distance from `0.500` on both axes. If the horizontal displacement is greater than or equal to vertical displacement, it checks Left and Right first. It then checks Up and Down. If none match, it returns Center.

This means diagonal eye movement is forced into a single dominant-axis class. It also means horizontal movement wins ties.

## Temporary Guided Calibration

Guided calibration is available from the existing gaze debug panel via `Start Calibration`.

Calibration sequence:

- Center for 5 seconds
- Left for 5 seconds
- Right for 5 seconds
- Up for 5 seconds
- Down for 5 seconds

For each stage, the calibration store records:

- Detected direction
- Averaged horizontal ratio
- Averaged vertical ratio
- Left eye horizontal ratio
- Right eye horizontal ratio
- Left eye vertical ratio
- Right eye vertical ratio

After all stages complete, personalized thresholds are generated by midpoint separation:

- Left threshold: midpoint between observed Left horizontal median and Center horizontal median
- Right threshold: midpoint between Center horizontal median and observed Right horizontal median
- Up threshold: midpoint between observed Up vertical median and Center vertical median
- Down threshold: midpoint between Center vertical median and observed Down vertical median

If a required stage has no valid samples, the default threshold is retained for that boundary.

## Accuracy Report

For each target direction, the calibration report shows:

- Detected frames
- Total frames
- Percentage
- Confusion cases for Center, Left, Right, Up, and Down
- Observed ratio ranges for averaged horizontal and vertical ratios
- Observed ratio ranges for left/right eye horizontal and vertical ratios

Important interpretation note: this is a guided self-label test, not a ground-truth eye-tracking validation. The target label is inferred from the calibration prompt. It can reveal practical usability errors, but it cannot prove absolute gaze accuracy.

## Robustness Assessment

Lighting sensitivity: high. The current method depends on MediaPipe iris landmarks. Uneven lighting, glare on glasses, shadows, low exposure, and motion blur can shift or destabilize iris landmarks. There is no image-quality score or low-confidence rejection path in the gaze module.

Camera placement sensitivity: high. Ratios are normalized per eye box, which helps with scale, but webcam height, lens angle, face distance, and screen-camera offset change the apparent iris position. A single fixed threshold set is unlikely to transfer well across users and devices.

Head movement influence: high. The gaze module does not compensate for head pose. When the user turns or tilts their head, iris position inside the eye box can change even if gaze target is unchanged. A separate head pose module exists, but this audit intentionally does not fuse it with gaze.

## Research Assessment

Current level: Prototype.

The module is useful as a live heuristic and debugging aid, but it is not research-grade.

Strengths:

- Simple, understandable normalized iris-ratio method.
- Separates raw ratio estimation from direction classification.
- Provides rolling/session metrics.
- Includes a guided temporary calibration flow.
- Generates per-direction confusion counts during calibration.

Weaknesses:

- No landmark confidence or frame quality gating.
- No head-pose compensation.
- No screen geometry model or camera-to-screen calibration.
- No subject-independent validation dataset.
- No labeled ground truth from an eye tracker.
- No repeated-trial reliability statistics.
- No lighting, camera position, glasses, or demographic subgroup testing.
- Direction classes are coarse and threshold-based.
- Diagonal gaze and near-boundary gaze are not represented.
- Calibration assumes the user follows prompts accurately.

## Recommended Improvements

1. Keep the current debug/calibration panel as temporary validation tooling, then hide it behind a development flag before production.
2. Add sample-quality gating using face/iris landmark availability, eye openness, face size, and frame-to-frame landmark stability.
3. Add repeated calibration trials and report median, interquartile range, and standard deviation per direction.
4. Add a minimum sample-count requirement before accepting personalized thresholds.
5. Add a confidence score for each gaze decision based on distance from thresholds and recent stability.
6. Store calibration reports with timestamp, camera setup notes, lighting condition, and user/device identifier.
7. Validate across multiple lighting conditions: bright front light, dim light, side light, backlight, glasses glare.
8. Validate across camera placements: eye-level, below-screen, above-screen, left/right offset, near/far face distance.
9. Validate head movement separately by asking the user to hold gaze target while moving head slightly left, right, up, down, and tilted.
10. For research-grade work, compare outputs against labeled gaze targets or an external eye tracker and report per-class precision, recall, F1, confusion matrix, and confidence intervals.

## Final Conclusion

The current gaze implementation is a functional prototype with useful live instrumentation and a practical temporary calibration test. Personalized thresholds should improve per-user behavior, but the method remains sensitive to lighting, camera placement, and head movement. It should not be treated as research-grade until it is validated against ground truth under controlled and varied conditions.
